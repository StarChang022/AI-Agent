## 一、已定案

### 1. 部署平台

| 項目 | 決定 |
|---|---|
| 主機 | Cloudflare Pages（使用 Pages Functions 處理表單） |
| Repo | 獨立 repo `quickey-landing`，先搬過去再在新 repo 實作 |
| 建置指令 | `pnpm build:pages`（等同 `pnpm build`：用 vite-ssg 在 Node 端預渲染，不需要瀏覽器） |
| 輸出目錄 | `dist` |
| 網域 | `quickey.com.tw`（DNS 已在 Cloudflare） |
| 原專案的 `landing/` | 不在本任務範圍，本任務不動原專案 |

### 2. 聯絡表單：寄信與備份

表單送出後做兩件事：**寄信到團隊信箱（主要）**，並**把資料備份到 Google 試算表**。兩條路互相獨立，其中一條失敗，另一條仍然會留下資料。

**寄信**

| 項目 | 決定 |
|---|---|
| 寄信服務 | **Resend**，使用免費方案（每月 3,000 封、每天 100 封） |
| 不採用 | Gmail API（設定和授權維護成本高）、SendGrid（已取消免費方案） |
| 寄件人 | `Quickey 官網 <noreply@quickey.com.tw>`，需在 Resend 驗證網域 |
| 收件人 | `service@playplus.com.tw`，設在環境變數 `MAIL_TO`，不寫進程式 |
| 回覆對象 | 在信件按「回覆」會回給填表人的 Email |
| 信件標題 | `[官網留言] {需求類別}｜{姓名}` |
| 信件內容 | HTML 加純文字備援，列出所有填寫的欄位：欄位標題粗體，需求說明不加標題、放在灰底框裡。填表內容一律先轉義，不讓填表人塞 HTML 進信裡 |
| 寄給填表人的確認信 | **不做** |

**備份到 Google 試算表**

| 項目 | 決定 |
|---|---|
| 串接方式 | **Google Apps Script**：在試算表裡發布一個網頁應用程式網址，官網把資料送到這個網址，新增一列 |
| 不採用 | Cloudflare D1（查看資料要寫 SQL，不方便同事使用）、Google Sheets 官方 API 加服務帳號（在 Cloudflare 上不好實作） |
| 欄位 | 時間、姓名、公司、Email、電話、需求類別、需求說明、寄信成功（是／否） |
| 防亂送 | 送資料時要附上一組密碼，密碼不符就不寫入 |
| 防公式注入 | 寫入的內容一律當文字處理，填表人填「=公式」也不會被執行 |
| 送出時機 | 在背景送，不讓填表人多等；寄信失敗也照樣寫入，並標記「寄信成功：否」 |
| 失敗通知 | **要做**（2026-11-04 由「不做」改為要做，見 D14 和下方「試算表失敗通知」） |
| 執行紀錄 | Apps Script 和 Pages Functions **都不可以印出表單內容**（例如 `console.log`），只記錄錯誤原因，免得執行紀錄又多一個要刪資料的地方 |
| 誰建立 | 前端開發提供 Apps Script 程式碼與步驟；內部人員用 `playplus.com.tw@gmail.com` 建立試算表並部署（見附錄 A、D13） |

**試算表失敗通知**

| 項目 | 決定 |
|---|---|
| 什麼時候寄 | 官網後端把資料送到 Apps Script 後，**連不上**（例如網址換了、Google 故障）或**回應失敗**（例如密碼不符、找不到「留言」工作表）時，每失敗一筆就寄一封 |
| 什麼時候不寄 | 沒有設定 `SHEET_WEBHOOK_URL` 或 `SHEET_TOKEN`（本來就不備份）；沒有設定 `ALERT_TO` |
| 誰寄 | 官網後端用 Resend 寄，跟留言信同一把金鑰；寄件人同 `MAIL_FROM`。Google 那邊不參與寄信 |
| 收件人 | `service@playplus.com.tw`，設在環境變數 `ALERT_TO`，不寫進程式；可以填多個，用逗號分隔 |
| 信件標題 | `[官網] 試算表備份失敗` |
| 信件內容 | 純文字，只寫：失敗時間（台灣時間）、失敗原因、這一筆的留言信有沒有寄成功，以及處理方式（留言信有寄成功：資料在信箱，修好試算表後從信件手動補進去；留言信也失敗：填表人當下會看到寄送失敗，通常會再送一次）。**不放姓名、Email、電話、留言內容等任何表單資料** |
| 通知信寄不出去 | 只在執行紀錄記錄錯誤原因，不重試。Resend 本身故障時通知信也寄不出去，這種情況沒有通知 |
| 不影響填表人 | 通知在背景執行，結果不影響填表人看到的畫面 |
| 寄信額度 | 通知信也算在 Resend 免費額度內（每天 100 封）。試算表壞掉期間每一筆留言都會多一封通知，以官網留言量來說足夠 |

### 3. 聯絡表單：機器人驗證

- 改用 **Cloudflare Turnstile**，取代現在只是勾選框的「我不是機器人」。
- 伺服器端先驗證 Turnstile，通過才寄信和備份。
- 驗證只能用一次：送出失敗或驗證過期時，驗證會重新進行。
- **這一版不做寄信頻率限制**。防灌信只靠 Turnstile，如果上線後被灌信，再到 Cloudflare 後台加 Rate Limiting 規則，不用改程式。

### 4. 聯絡表單：欄位規則（伺服器端會再檢查一次）

| 欄位 | 規則 |
|---|---|
| 姓名 | 必填，最多 50 字 |
| 公司名稱 | 選填，最多 100 字 |
| Email | 必填，格式要正確，最多 100 字 |
| 聯絡電話 | 選填，最多 30 字 |
| 需求類別 | 必填，只能是：產品諮詢／功能建議／合作洽談／其他問題 |
| 需求說明 | 必填，最多 2000 字（2026-11-05 取消至少 5 個字的限制） |
| 同意隱私權政策 | 必須勾選 |

- 單行欄位會去掉換行，防止有人在信件標頭夾帶內容。
- 不合規則時，伺服器擋下並回傳錯誤，不會寄信，也不會備份。

### 5. 聯絡表單：送出結果

- **成功**：顯示成功畫面，清空表單。
- **失敗**（寄信服務異常、網路中斷）：在「送出需求」按鈕**正上方**用紅字顯示「寄送失敗，請稍後再試」，不附 Email。訊息會一直留著，下次送出時才清掉，**保留已填的內容**，可以再送一次。訊息要讓螢幕閱讀器能讀到（無障礙）。不用 toast。
- 送出中按鈕無法再按，避免重複送出。
- 成功與否**以寄信結果為準**，試算表只是備份。

### 6. 資料保存

- 信箱和試算表裡的表單資料**都先保留，不做定期刪除**。
- 有人要求刪除個資時，信箱和試算表都要刪（做法見附錄 B）。
- Resend 的寄信紀錄保留 30 天後自動刪除，不用處理。
- 內部要做到兩件事，「不寫年限」的寫法才站得住腳（顧問建議）：
  1. 垃圾留言和測試留言看到就刪
  2. 留言名單沒有另外取得同意之前，不拿來寄行銷信或上線通知
- 隱私權政策的保存期間不寫具體年限，條文見 `顧問-隱私權條文.md`（只留本機，不進 git）。保存依據寫「蒐集目的存續期間，以及後續業務聯繫、洽詢或處理爭議所必要之期間」；目的消失時承諾「刪除或停止利用」。不要寫「永久保存」或「期滿將刪除」這類做不到的承諾。
- **請律師優先確認**：「只在有人要求時才刪」是否符合個資法第 11 條要求的主動處理。

### 7. 環境變數（在 Cloudflare Pages 後台設定）

| 名稱 | 類型 | 內容 | 誰提供 |
|---|---|---|---|
| `RESEND_API_KEY` | Secret | Resend 的 API 金鑰 | 用戶申請 |
| `TURNSTILE_SECRET_KEY` | Secret | Turnstile 的伺服器端金鑰 | 用戶申請 |
| `SHEET_WEBHOOK_URL` | Secret | Apps Script 部署後的網址 | 內部人員部署後提供 |
| `SHEET_TOKEN` | Secret | 送資料到試算表時附上的密碼 | 內部人員自訂 |
| `MAIL_TO` | 一般變數 | `service@playplus.com.tw` | 已定 |
| `MAIL_FROM` | 一般變數 | `Quickey 官網 <noreply@quickey.com.tw>` | 已定 |
| `ALERT_TO` | 一般變數 | `service@playplus.com.tw`（試算表失敗通知的收件人；Preview 可填測試信箱或不填） | 已定 |
| `VITE_TURNSTILE_SITE_KEY` | 一般變數（建置時用） | Turnstile 的前端金鑰 | 用戶申請 |
| `VITE_SITE_URL` | 一般變數（建置時用） | `https://quickey.com.tw` | 已定 |
| `NODE_VERSION` | 一般變數（建置時用） | `22` | 已定 |
| `PNPM_VERSION` | 一般變數（建置時用） | `10.23.0`（固定版本，與本機一致） | 已定 |

本地開發的金鑰放在 `.dev.vars`，這個檔案必須加進 `.gitignore`。開發期間用 Turnstile 的官方測試金鑰，試算表另建一份測試用的。

### 8. 用戶或內部人員需要自己在後台做的設定

1. 註冊 Resend，加入網域 `quickey.com.tw`，照它給的值在 Cloudflare DNS 加紀錄，完成驗證。
2. 在 Cloudflare 後台建立 Turnstile，取得 site key 和 secret key。
3. 用 `playplus.com.tw@gmail.com` 建立備份試算表並部署 Apps Script（附錄 A）。
4. 在 Cloudflare Pages 專案設定裡填入第 7 點的環境變數。

## 附錄 A：建立備份試算表（內部人員操作）

1. 用 `playplus.com.tw@gmail.com` 新增試算表，工作表命名為「留言」，第一列填：時間、姓名、公司、Email、電話、類別、內容、寄信成功
2. 「擴充功能」→「Apps Script」，貼上前端開發提供的程式碼，填入自訂的密碼
3. 「部署」→「新增部署作業」→ 類型選「網頁應用程式」；執行身分選「自己」，存取權選「所有人」
4. 把部署後的網址和密碼交給開發，設成 Cloudflare 的 Secret

**注意事項（失敗大多來自人為改設定）**

- 修改程式後要用「管理部署作業」編輯**原本那一個**部署，不要新增；新增的話網址會變，官網就送不進來
- 不要改工作表名稱「留言」，也不要刪掉這個工作表
- `playplus.com.tw@gmail.com` 要開啟兩步驟驗證；知道密碼的人離職或異動時要改密碼（能登入這個帳號就能看到所有留言者的個資）
- 試算表只共用給需要看的人；共用的人離職時要移除共用
- 每次改過 Apps Script 或試算表後，自己送一筆測試留言，確認信箱和試算表都有收到，而且**沒有**收到「試算表備份失敗」通知

## 附錄 B：有人要求刪除個資時（內部人員手動作業）

1. 信箱：搜尋對方的 Email，刪掉相關信件，再清空垃圾桶
2. 試算表：搜尋對方的 Email，刪掉那幾列。注意：刪掉的資料在試算表的「版本記錄」裡還看得到，隱私權政策第八條已寫明「因系統備份或版本紀錄無法立即完全移除的部分，會停止利用並限制存取」（請律師確認是否足夠）
3. 回覆對方，告知已經刪除

建議先在信箱設一個篩選器：寄件者 `noreply@quickey.com.tw` 的信自動貼上「官網表單」標籤，之後比較好找。
