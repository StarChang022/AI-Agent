# 後端審查：電子發票 QR 解碼（2026-10-28）

範圍：`feat/ocr-qrcode` 的 `git diff --cached`（6 個檔）。對照 `docs/OCR辨識規格.md` §3.2、§4。
只讀不改 `app/`；示範寫法在 `docs/reviews/2026-10-28/qr-scanner-限縮示範.rb`。

## 結論

- **有 3 項必修**：超大像素的圖片擋不住（M-1）；品名裡有一個 Big5 罕見字，整個檔案的 QR 結果（連號碼、日期、金額）都會被丟掉（M-2）；PDF 改用 `pdftoppm` 後，超大頁面會在被拒絕前先渲染完（M-3）。
- **第二版（`pdftoppm`）**：參數是陣列、不經 shell；超時有 `KILL` 並回收；暫存資料夾一定清掉；自己讀 PGM 時表頭與像素數量都有檢查，不會讀錯或崩潰。缺的是 `ensure` 保險與資源上限，見第二版一節。
- libzbar 找不到時退回原流程：**實測通過**。FFI 呼叫的記憶體釋放順序看起來正確，但**本機沒有 libzbar，這部分沒實際跑過**（見最後「測試方式」）。
- 欄位位置、16 進位金額、Big5 轉換、`conflicts.invoices` 清空、單張行為、統編檢查碼與稅率搬移：**符合規格，沒有發現會讓程式中斷的輸入**。
- 另有 8 項建議，不擋合併。

## 必修

### M-1　超大像素圖片繞過 3 秒時限（影響第 2 點）

3 秒只在「每頁開始前」檢查，單頁卡多久都不管；縮圖（`MAX_EDGE`）又是**讀完整張圖之後**才縮，擋不住讀圖本身。5MB / 5 檔的上傳限制（`ReceiptAttachmentValidation`）只管位元組，壓縮率高的檔案不受限。

實測（libvips 8.16.1，本機）：390KB 的 PNG（20000×20000 全黑）讀圖+縮圖 2.2 秒、CPU 8.5 秒，這還沒算 zbar。（第一版的 PDF 用 libvips 讀，實測 333 bytes 的 PDF 要 37 秒、1GB；第二版改 `pdftoppm` 後這條路已不存在，新的 PDF 風險見 M-3。）

**為什麼要緊**：這個請求在 Google 之前跑；Google 若拒絕該檔（`InvalidDocument`）不扣次（`ocr_controller.rb:66`、`:71`），所以登入的使用者可以不花次數、重複送，每次佔住一條 Puma thread 加上全部 CPU。

**修法**（已驗證，示範檔）：`new_from_buffer` 是延遲讀取，先看 `width * height`，超過 1 億像素直接略過（20000×20000 圖在讀檔頭時就略過）。HEIC 轉 JPEG（`ocr_controller.rb:108`，既有程式）也沒有像素上限，可一併加。

### M-2　品項區任何錯誤都會丟掉整份 QR（影響第 3 點）

`InvoiceQr#text` 對 Big5 做 `value.encode(UTF_8)`。Ruby 的 Big5 有 **847 個**「編碼合法、但沒有 Unicode 對應」的雙位元組（例如 `A3C0`），`valid_encoding?` 擋不住，`encode` 會丟 `Encoding::UndefinedConversionError`。實測：品名含 `\xA3\xC0` → `InvoiceQr.call` 直接 raise → controller 的 `scan_invoices` rescue 回 `[]` → **號碼、日期、金額、統編全部白白丟掉**，退回全文規則。

同一類：QR 裡的數字是 400 位數（`"9"*400 + ".5"`）→ `to_f` 變 Infinity → `.round` 丟 `FloatDomainError`，同樣整份丟掉。

不會當機，但違反規格的精神（品項是加分項，QR 表頭是可靠資料）。

**修法**（示範檔）：`encode(..., undef: :replace, replace: "")`；品項區整段包 `rescue StandardError → []`，表頭欄位照用。順便把 Big5 改用 `CP950`，無法轉換的組合從 847 降到 62（台灣 POS 多半是微軟碼表）。

### M-3　`pdftoppm` 先渲染完才檢查像素上限（第二版，影響第 5 點）

`MAX_PDF_PIXELS = 35_000_000` 是在 `read_pgm` 才檢查，這時 `pdftoppm` 已經把整頁渲染、寫進磁碟。實測（pdftoppm 25.04，`-r 300 -gray`）：

| 輸入（單頁 PDF） | 結果 |
|---|---|
| MediaBox 3600×3600 pt（2.25 億像素） | 2.4 秒、**RSS 450MB、磁碟寫入 225MB**、exit 0；之後 `read_pgm` 才拒絕 |
| MediaBox 7200×7200 pt | 3 秒被 `KILL`，磁碟已寫 47MB 的半成品（目錄之後有清掉） |
| MediaBox 14400×14400 pt | poppler 自己放棄，只寫出 12 bytes、exit 0；`read_pgm` 回 nil，安全 |

所以上限擋得住「進到 zbar 的資料量」，擋不住「`pdftoppm` 自己花的記憶體、磁碟與時間」。多個併發請求時 450MB × 同時請求數會吃光記憶體。

**修法**（已驗證）：把 `-r 300` 換成 `-scale-to 3600`（長邊固定 3600px，與 `MAX_EDGE` 一致）。同一個 14400pt 頁面得到 3600×3600、13MB 的 PGM。A4 約 307 dpi，QR 解碼沒差別。這樣 `MAX_PDF_PIXELS` 與後面的 `resize` 都幾乎不會觸發，可保留當保險。

## 第二版（`pdftoppm` 取代 libvips 讀 PDF）

| 檢查項 | 結果 |
|---|---|
| 1. `Process.spawn` 參數 | **安全。** 傳的是多個字串（`Process.spawn(*command, …)`），不經 shell；`pdf_path` 是 `Dir.mktmpdir` 內的固定檔名 `source.pdf`，沒有使用者可控的字串，也沒有以 `-` 開頭的參數注入。輸入輸出都導向 `File::NULL`。小建議：子程序會繼承 Rails 的環境變數（含資料庫密碼、Google 金鑰），而 `pdftoppm` 是在解析**不受信任的 PDF**，建議 `unsetenv_others: true` 並自己帶 `PATH`。 |
| 2. 超時有沒有 KILL、有沒有收回 | **正常路徑沒問題。** 超過 `@deadline` → `Process.kill("KILL")` → `Process.wait`，不留殭屍、不留孤兒；`Process.wait2(WNOHANG)` 在正常結束時也已回收。**缺口：** `spawn` 之後到 `kill` 之前如果 Ruby 這條 thread 被中斷（Puma 關閉、`Timeout`、其他例外），沒有 `ensure`，`pdftoppm` 會變成孤兒繼續跑到結束，而 `mktmpdir` 已經把目錄刪了。建議用 `begin … ensure` 包住，離開時若 `Process.wait2(pid, WNOHANG)` 還沒回收就 `KILL` + `wait`。 |
| 3. 暫存資料夾 | **一定清掉。** 用的是區塊形式 `Dir.mktmpdir { }`，例外、`break`（`call` 裡超時 `break`）、`next unless pdftoppm(...)` 離開區塊都會刪；目錄權限 0700。實測超時被 KILL 後目錄也已移除。唯一不會清的是 Ruby 程序本身被 `kill -9` / OOM 時，這屬於容器層面，可接受。小提醒：程式沒有 `require "tmpdir"`，在 Rails 裡因其他套件已載入而沒問題。 |
| 4. 讀 PGM | **不會讀錯或崩潰。** 實測 16 種輸入：表頭寫的尺寸大於實際資料 / 只有表頭 / 空檔 / 表頭被截斷 → `nil`；資料多於表頭 → 只讀 `寬×高` 個位元組；`maxval` 65535、`P2`、表頭含註解 → `nil`；尺寸 99999×99999、30 位數 → `nil`（先比 `MAX_PDF_PIXELS`，沒有整數溢位問題，Ruby 是大整數）；35,000,000 像素剛好 → 34ms 讀入。`new_from_memory_copy` 的長度 = 寬×高×1，libvips 不會讀到範圍外。**唯一例外：** 表頭寫 `0` 寬或高時 `new_from_memory_copy` 丟 `Vips::Error`（並印 GLib 警告），被 `call` 的 `rescue` 接住、後面的頁就不解了。`pdftoppm` 自己不會產出 0，建議仍加 `return nil if width.zero? || height.zero?`。 |
| 5. 上限夠不夠 | 10 頁、300 dpi 灰階對電子發票 QR 夠用。**單頁 3500 萬像素擋不住的原因見 M-3。** 另一個建議：現在是「一次轉完 10 頁，超時就整個丟掉」，一份掃描檔每頁較重時，3 秒內轉不完就連第 1 頁也沒有。可改成逐頁 `-f N -l N` 轉、轉完一頁解一頁，超時時保留已解的頁；或超時時只保留已寫完的頁（最後一個檔案是半成品，丟掉）。 |

另外：`pdftoppm` 解析失敗（損壞的 PDF）exit 1 → `status.success?` false → 整個 PDF 當沒有 QR，行為正確。`Dockerfile` 加 `poppler-utils` 與 `libzbar0t64` 在 `base` 階段，build 與正式映像都有。

## 逐項回覆你的 5 點

### 1. ffi / libzbar：記憶體、崩潰、找不到時退回

- **找不到 libzbar → 安全退回：實測通過。** 本機沒有 libzbar，`QrScanner.call` 連呼叫 3 次都回 `[]`，只 log 一次 warn（`defined?(@zbar)` 讓之後不再重試），髒資料（`'abc'`）也回 `[]`，不丟錯。`LoadError` 與 `FFI::NotFoundError`（缺符號）都有接。
- **釋放順序（靜態檢查，對照 zbar.h 0.23）：** `zbar_image_destroy` 先、`scanner_destroy` 後，符合 zbar 的規則（symbol 屬於 image，recycle 回 scanner）；`set_data` 的 cleanup 傳 `nil`，zbar 不會去 free Ruby 的 `MemoryPointer`；symbol 的資料在 destroy 之前就用 `read_bytes` 複製出來；`ensure` 在 `zimage` / `scanner` 尚未建立時也安全。簽章（`:ulong` 的長度與 fourcc、`:uint` 的長度、`ZBAR_QRCODE = 64`、`Y800` 的 fourcc）都對。每次 `scan` 各建各的 scanner，多執行緒沒有共用狀態；`zbar_scan_image` 設 `blocking: true` 放掉 GVL，不會卡住其他請求。
- **崩潰：** zbar 本身若有 C 層 bug，Ruby 攔不到（`rescue StandardError` 不涵蓋 segfault）。唯一能做的是限制輸入（只開 QR code 這點已做；像素上限見 M-1）。MVP 可接受。
- **沒驗證到的：** 我沒辦法在本機跑真正的 zbar，上面是對照原始碼與標頭的靜態判斷。**建議開發在 Docker 裡拿 4 張真實發票照片 + 1 份多頁 PDF 實跑一次，並用 `valgrind` 或連跑 200 次看 RSS 是否持平。**

### 2. 時限與縮圖擋不擋得住惡意輸入

見 M-1、M-3。多頁（上百頁）擋得住（第二版 `-l 10` 只轉前 10 頁，3000 頁 PDF 實測轉 10 頁很快）；單頁巨大（壓縮圖、超大 PDF 頁面）擋不住。

### 3. `invoice_qr` 格式與錯誤處理

- 欄位位置（10 + 7 + 4 + 8 + 8 + 8 + 8 + 24 = 77 碼）、16 進位金額、`:` 分段（自用區 / 筆數 / 總筆數 / 編碼 / 品項）、右 QR 以 `**` 開頭（有無接 `:` 都能解）、編碼 2（Base64）不用品項：**符合財政部格式與 §3.2**。
- 實測 30 種輸入，**沒有任何一種讓程式中斷**：空字串、nil 欄位以外的截斷（半截、77 碼後無冒號、無品項段、筆數 0 / 對不上）、日期 `1150230` / `0000101` / `1159999`、總計 < 銷售額、賣方統編錯、網址、Big5 無效位元組、`1e5`、品名含冒號。這些不是回 `[]` 就是只讓 `items` 為 `[]`。
- 會 raise 的只有 M-2 說的兩種（Big5 無對應字、超長小數），而且 controller 有 `rescue`，不會變 500。
- `QrScanner` 不會回 nil 的 `data`，所以 `code[:data].b` 對 nil 的 NoMethodError 不會發生。

### 4. `result_merger` 與 `conflicts.invoices`

- 2 張以上：`merged` 的 `documentType`、日期、統編、發票號碼、稅率、未稅、稅額、金額全為 `null`；`merged.items = []`；`conflicts.fields` 與 `conflicts.items` 都是 `[]`；賣方名稱（全文抓的）照常比對，`lowFields` 只剩 `counterpartyName`；`warnings` 多一句「辨識到 N 張發票，請選擇要帶入哪一張」。**照規格。**
- 清空是對**所有檔案**做的（含沒有 QR 的檔案），與規格「本次送的檔案…不進 merged」一致（同一次送的是同一張憑證的多張照片）。
- 跨檔案同號碼只列一次；某個檔案只有 1 張、另一個檔案有 2 張時，這 1 張也列入挑選清單且它的 QR 欄位同樣被清空。對。
- `conflicts.invoices` 的鍵是 snake_case（`source_index`、`unit_price`…），前端 `api/service.ts` 統一轉 camelCase，和規格範例一致。
- **單張發票：** `conflicts` 只有 `fields` / `items`（沒有 `invoices` 鍵），`merged` 欄位照 QR；與以前不同之處都是規格要的——QR 欄位 HIGH 0.9、QR 沒有的欄位（例如銷售額 `00000000` 時的未稅 / 稅額、沒有買方時的我方統編）**不保留**全文抓到的值。QR 失敗或不是發票 QR 時，`apply` 原樣回傳，行為與改動前完全一樣。
- `recognized?` 加 `invoices.present?` 合理：多張發票時欄位被清空，不加會被誤判為「未辨識出內容」。

### 5. 統編檢查碼與稅率推導

- `valid_tax_id?` 與 `derive_tax_rate` 只是**從實例方法搬成類別方法**，邏輯逐行相同（我對過 diff），`TAX_ID_WEIGHTS` 等常數在類別內可解析。原本的呼叫端改為 `self.class.…`，沒有漏。
- 稅率行為不變；新增的行為差異只有 S-3（QR 路徑的稅額是算出來的）。
