# 代墊款管理工具 PRD

---

## 0. 使用者痛點與需求分析

| 痛點 | 現狀問題 | 目標用戶受影響情況 | 我們的解決方案 |
|-----|---------|------------------|--------------|
| **記錄流程複雜冗長** | 使用 Notion 或紙張記錄，手機體驗差、填寫慢（5 分鐘/筆） | 員工每週 2-3 筆，月均浪費 30-60 分鐘 | 專用移動應用，快速填寫（1 分鐘/筆） |
| **容易誤改他人記錄** | 無權限控制，Notion 中所有人都能編輯 | 已發生 1-2 次誤改，造成對帳困難 | 角色權限管理，每人只能編輯自己的記錄 |
| **容易遺漏記錄** | 沒有提醒機制，員工常忘記記錄 | 月末才發現有遺漏，難以追溯 | 自動提醒、簡化流程鼓勵主動記錄 |
| **統計困難** | 行政人員手動統計，容易出錯 | 月末對帳需 2-3 小時 | 自動統計、多維度報表（員工/類別/時間）|
| **審核流程不清晰** | 沒有明確的審核規範 | 員工不知道什麼時候能拿到錢 | 明確的審核流程、實時狀態通知 |

## 1. 產品概述

**產品名稱：** 代墊款管理工具

**平台：** Web 應用、iOS/Android 原生應用（第一版本為 Web 優先）

**產品描述：**

一個通用的員工代墊款管理工具，適用於各行業。員工可以便捷地記錄代墊的各類費用（如材料、工具、差旅、服務費等），並上傳發票；行政/財務人員可以從後台查看所有員工的代墊款項統計，並進行核銷和發放作業。工具致力於簡化記錄流程、減少手動錄入負擔，並提供清晰的數據統計，提升工作效率。

---

## 2. 目標用戶

- **基層員工/執行人員：** 需要經常代墊工作相關費用（材料、工具、差旅、服務費等），並需要便捷的手機端記錄方式。目標用戶為各行業的小型至中型團隊（5-50人），使用頻率約每週 2-3 次。典型行業包括工程、建築、律師事務所、廣告代理、設計公司、醫療診所、餐飲連鎖等。

- **行政/財務人員：** 負責收集、匯總代墊款項資訊，核銷發票，並與管理層溝通發放時程。需要清晰的數據視圖和統計功能。

- **公司管理者：** 了解公司總代墊支出，決定是否與薪資一起發放或單獨處理，監控代墊款政策執行。可設定權限政策。

## 3. 核心功能

### 3.1 員工端 - 代墊記錄

| 功能 | 描述 |
|-----|------|
| 快速填寫 | 輸入金額、選擇代墊費用類別、簡短描述（用途、日期、地點等） |
| 拍照上傳 | 用手機相機拍攝發票或收據，直接附加到記錄 |
| 提交狀態 | 記錄提交後自動標記為「待審核」或「未核銷」狀態 |

### 3.2 員工端 - 數據查看

| 功能 | 描述 |
|-----|------|
| 個人統計 | 清晰的卡片展示已核銷/待審核/未核銷金額統計，本月/歷月統計 |
| 代墊歷史 | 分頁展示每筆代墊記錄的日期、類別、金額、狀態、核銷進度 |

### 3.3 行政/財務端 - 後台統計面板

| 功能 | 描述 |
|-----|------|
| 月度匯總 | 展示所有員工的代墊總額、分員工的詳細清單、待審核/待發放金額 |
| 狀態管理 | 逐筆審核記錄，標記為「已核銷」或「已發放」，更新員工端狀態 |
| 發票查閱 | 點擊記錄可查看上傳的發票照片，進行核實 |

### 3.4 費用類別管理

| 功能 | 描述 |
|-----|------|
| 預設類別 | 系統內建常見代墊費用類別（材料、工具、差旅、服務費、其他），加速員工填寫 |
| 自定義類別 | 員工或行政可新增組織特定的費用類別（如客戶餐飲、培訓費等） |

## 4. 附加功能

| 功能 | 描述 |
|-----|------|
| 自動通知 | 代墊款項狀態變更時（待審核、已核銷、已發放），自動通知相應員工（Email/推播） |
| 權限控制 | 管理者可設定不同員工角色的可見範圍（是否可看其他人的代墊記錄、是否可修改他人記錄） |
| 導出報表 | 行政/財務可導出 CSV、Excel 或 PDF 格式的月度統計報表，支援按員工、費用類別、時間段篩選 |
| 多層級審核流程 | 支援自訂審核流程（員工提交 → 部門主管審核 → 財務複核 → 發放） |
| 備註與溝通 | 員工和審核人員可添加備註或審核意見，在線溝通而無需另外郵件往返 |

## 9. 風險和挑戰

| 風險 | 影響 | 應對方案 |
|-----|------|---------|
| **用戶採納率低** | 員工習慣舊流程（紙張、郵件、Notion），可能不願轉換 | 清晰的操作指引、完整的培訓影片、管理層推動、初期提供專人支持 |
| **憑證完整性問題** | 員工可能遺漏或偽造發票，導致核銷困難 | 允許多種憑證形式，建立清晰的審核標準和政策，設定提醒機制 |
| **資料安全與隱私** | 涉及員工個人資訊和財務紀錄，可能引發隱私顧慮 | 端到端加密、嚴格的存取控制、定期安全審計、符合法規（GDPR、個資法） |
| **多行業適配性** | 通用設計可能無法完全滿足特定行業需求 | 先在 2-3 個代表行業驗證核心痛點，後期提供行業特定模組 |
| **競爭壓力** | Notion、Google Forms 等已被廣泛使用 | 強調專業性、合規性、審核流程、集成能力等差異化優勢 |

## 11. 技術棧建議與成本估算

### 技術棧選擇

| 層級 | 建議技術 | 理由 | 成本估算 |
|-----|---------|------|---------|
| **前端** | React 18 + TypeScript + Tailwind CSS | 快速開發、易於維護、響應式設計 | 4 週（2 人） |
| **後端** | Node.js + Express + TypeScript | 與前端同語言、生態成熟、開發效率高 | 6 週（2 人） |
| **數據庫** | PostgreSQL | 關係型、免費開源、支援複雜查詢 | 配置已含 |
| **檔案儲存** | AWS S3 或 MinIO（本地） | 可靠、成本低、支援大規模 | 按量付費 |
| **認證** | JWT + Session | 安全、業界標準 | 已含開發 |
| **通知** | Email（SMTP）+ 推播（Firebase/OneSignal） | 覆蓋廣、可靠 | 第一版本 Email 優先 |
| **部署** | Docker + AWS EC2 或 DigitalOcean | 易於部署、可伸縮 | 10 美元/月起 |

### MVP 開發時間線（快速版）

> 💡 **建議策略：** 先做 4 週的極簡 MVP（只有 P0 功能），盡快進入真實環境驗證，而不是在開發階段花太多時間。

| 階段 | 工作內容 | 人力需求 | 時間 | 說明 |

| **Week 2-4: 前端開發** | 頁面實現、表單、發票上傳、基礎統計 | 1-2 人 | **3 週** | 與後端並行，UI 優先易用性 |

### 分階段開發計畫

#### **Phase 1: 極速 MVP（Week 1-6）— 只做 P0 核心功能**

簡化項目：
- ✅ 員工：填金額 + 類別 + 拍照發票 + 提交
- ✅ 行政：看所有記錄 + 查發票照片 + 標記已發放
- ❌ 暫時移除：權限控制、多層級審核、複雜報表、自訂類別

**代碼複雜度低 → 開發快 → 快速驗證市場反應**

#### **Phase 2: 功能迭代（Week 7-12）— 根據反饋加入 P1**

根據 Beta 用戶反饋決定優先順序：
- 可能優先加：自動通知（用戶呼聲最高）
- 可能暫時跳過：複雜的多層級審核（用戶可能不需要）

#### **Phase 3: 穩定與擴展（Month 3+）— v2.0 版本**

- 根據 1-3 個月真實數據優化架構
- 加入行業特定模組
- 考慮 API 開放等

| **現有數據遷移計畫** | 評估是否遷移 Notion 歷史記錄，制定遷移方案 | 產品 + 行政 + IT | 開發前確認 | P1 |
| **用戶培訓資料準備** | 製作操作手冊、教學影片、常見問題 | 產品 + 行政 | 上線前 2 週 | P0 |
| **員工賬號同步** | 與公司 Active Directory 或 HR 系統對接 | 開發 + IT | 上線前 1 週 | P0 |
| **發票模板標準化** | 確認哪些類型發票可被接受 | 財務 + 行政 | 開發前 | P1 |
| **薪資系統接口** | 如需與薪資系統整合，確認接口規範 | 開發 + 財務 + IT | v1.0 後考慮 | P2 |
| **法規合規評估** | 確認數據保留期限、隱私政策等 | 法務 + IT | 上線前 | P0 |
| **安全認證** | 視組織要求進行安全審計（SOC 2、ISO 27001） | IT + 安全團隊 | 視需求 | P2 |

## 14. 通用版本與行業特定化策略

### 發展路線圖

```
第 1-3 個月：通用核心版本 (v1.0-1.1)
├─ 驗證 2-3 個代表行業的核心痛點（工程、律師、服務業）
├─ 保持功能通用，不做行業特定開發
├─ 收集各行業的反饋需求
└─ 目標：證明產品的通用價值

第 4-6 個月：根據用戶反饋迭代 (v1.2-1.5)
├─ 分析各行業的共同需求和差異
├─ 優先開發 80% 行業通用的功能
├─ 評估是否需要行業特定模組
└─ 目標：穩定用戶基數、驗證商業可行性

第 7-12 個月：行業特定模組化擴展 (v2.0+)
├─ 推出工程版、律師版、服務業版等專用模組
├─ 或開放 API 讓用戶自訂審核流程、費用類別
├─ 建立行業合作夥伴生態
└─ 目標：擴大市場份額、提升 ARPU
```

### 行業特定模組規劃

| 行業 | 核心需求 | 模組功能 | 優先順序 |
|-----|---------|---------|---------|
| **工程/建築** | 案場成本管理、人力排班 | 案場模組、工時記錄、物料庫存 | P1 (v2.0) |
| **律師事務所** | 按案件分類、客戶費用分攤 | 案件模組、費用分攤規則 | P1 (v2.0) |
| **廣告代理** | 按專案分組、客戶回溯 | 專案模組、客戶關聯、發票回溯 | P2 (v2.1) |
| **零售/餐飲** | 分店管理、供應商費用 | 分店模組、供應商管理 | P2 (v2.1) |
| **醫療診所** | 醫材費用、耗材領購 | 科室模組、醫材庫存、領購流程 | P2 (v2.1) |
