> 對應 PRD：`docs/產品規格文件.md`、`docs/sitemap.md`
> 對應分工決策：`docs/產品延伸分工討論.md`
> 命名以領域概念為主，欄位名採 camelCase（前端 TS）；後端 DB 對應 snake_case 由 ORM 自動處理。

---

## 一、決策摘要

**代墊款請款（Reimbursement）與 支出（Expense）採用兩個獨立 model，不合併。**

理由：

1. **業務語意不同**
   - Expense：公司對**外部廠商**付款（採購、訂閱、發票）
   - Reimbursement：公司對**內部員工**還錢（員工先自費，事後請款）
2. **生命週期不同**
   - Expense：登錄 → 撥款，通常直接成立、不需簽核
   - Reimbursement：提交 → 審核 → 核准 → 撥款，走 6 狀態機
3. **會計實務就是分開**
   - 應付帳款 (Accounts Payable, 21100) 與 應付員工代墊款 (21400) 傳票科目不同
4. **擴充方向會分岔**
   - Reimbursement 未來可能加：多層簽核、金額分級、預算前置校驗
   - Expense 未來可能加：定期扣款、廠商主檔關聯、發票稅務欄位

**串接方式**：Reimbursement 核准時 → 系統自動 create 一筆 Expense (`source='reimbursement'`)，並雙向關聯（`Reimbursement.expenseId` ↔ `Expense.sourceRefId`）。

## 二、核心模型

### 2.1 Reimbursement（代墊款請款）

員工提交的請款單。核准前是獨立佇列，不進統一支出列表、不算儀表板支出統計。欄位以前端 `frontend/src/types/domain.ts` 的 `Reimbursement` interface 為準（後端 schema 需對齊）。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid | PK |
| `employeeId` | uuid → User | 申請人 |
| `amount` | decimal(12,2) | 請款金額（含稅） |
| `categoryId` | text → Category | 支出類別（存 Category.id 字串） |
| `description` | text | 說明 |
| `incurredAt` | date | 費用發生日 |
| `receiptUrls` | text[] | 憑證檔案 URL 陣列（Stage B 後端可能改成 Attachment 表） |
| `receiptNames` | text[]? | 對應 `receiptUrls` 同 index 的原始檔名 |
| `documentType` | enum | `'invoice'` \| `'receipt'`（發票／收據） |
| `vendor` | text? | 廠商名稱 |
| `taxId` | text? | 統一編號 |
| `invoiceNo` | text? | 發票號碼 |
| `taxRate` | enum | `'business_5'` \| `'exempt_0'` |
| `preTaxAmt` | decimal? | 稅前金額 |
| `taxAmt` | decimal? | 稅額 |
| `status` | enum | 6 狀態機（見 §4.1） |
| `approvalProgress` | jsonb? | 簽核進度（含 steps[].reviewedBy / reviewedAt / comment，取代舊 submittedAt/approvedAt/approverUserId/rejectedReason 四欄） |
| `paymentMethod` | enum? | `'bank_transfer'` \| `'cash'`；已發放時填入 |
| `expenseId` | uuid? → Expense | 核准後產生的支出 ID（雙向關聯；若當下未成立則為 null） |
| `version` | int | 樂觀鎖版本號 |
| `createdAt` / `updatedAt` | timestamp | — |

### 2.8 RecurringTemplate（固定收支範本）

依週期自動產生待收款或待付款紀錄的範本。產生的紀錄是一般 Income 或 Expense，不屬於範本。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid | PK |
| `companyId` | uuid → Company | 所屬公司 |
| `direction` | enum | `'income'`（固定收入）\| `'expense'`（固定支出） |
| `categoryId` | text → Category | 對應 kind 與 direction 相同的類別 |
| `name` | text | 項目名稱 |
| `amount` | decimal(12,2) | 每期金額（含稅） |
| `frequency` | enum | `'monthly'`（每月）\| `'yearly'`（每年） |
| `dayOfMonth` | int | 1–31；31 等同月底（較短的月份產生在當月最後一天） |
| `monthOfYear` | int? | 每年週期才需要，1–12 |
| `startMonth` | text | 開始月份，格式 `YYYY-MM` |
| `endMonth` | text? | 結束月份，格式 `YYYY-MM`；空白表示持續產生 |
| `lastGeneratedPeriod` | text? | 已產生到的期數（例如 `2026-10`），用於避免重複產生 |
| `deletedAt` | timestamp? | 刪除時間（進入垃圾桶） |
| `createdBy` | uuid → User | 誰建立的 |
| `createdAt` / `updatedAt` | timestamp | — |

**產生規則**
- 每天檢查一次，依 `lastGeneratedPeriod` 之後、且在 `startMonth` 到 `endMonth` 之間的期數產生紀錄。
- 已刪除（有 `deletedAt`）或已到期的範本不產生。
- 修改金額、週期、名稱只影響尚未產生的期數。

### 2.10 Transfer（資金移轉）

帳戶之間的資金移轉，不屬於收入或支出，不計入損益、預算與儀表板，只影響帳戶餘額。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid | PK |
| `companyId` | uuid → Company | 所屬公司 |
| `fromAccountId` | uuid → Account | 轉出帳號 |
| `toAccountId` | uuid → Account | 轉入帳號（不可與轉出相同） |
| `amount` | decimal(12,2) | 移轉金額，必須大於 0 |
| `transferDate` | date | 移轉日期 |
| `note` | text? | 備註 |
| `attachments` | Attachment[] | 憑證（共用 §2.4 結構） |
| `feeExpenseId` | uuid? → Expense | 手續費自動產生的支出；沒有手續費時為空 |
| `createdBy` | uuid → User | 誰登錄的 |
| `deletedAt` | timestamp? | 刪除時間（進入垃圾桶） |
| `createdAt` / `updatedAt` | timestamp | — |

**手續費規則**：手續費大於 0 時自動產生一筆支出，類別為「手續費」，日期為移轉日期，帳戶為轉出帳號，狀態為已付款，並記錄於 `feeExpenseId`。編輯移轉時同步更新該支出金額；手續費改為 0 時，該支出移入垃圾桶並清空 `feeExpenseId`；刪除移轉時，該支出一併移入垃圾桶，還原移轉時一併還原。

## 三、支援模型

### 3.1 Company（公司）

MVP 一個系統一家公司；未來多租戶時擴充。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid | PK |
| `name` | text | 公司名（不強制 unique；同名公司真實存在） |
| `companyType` | enum | `'limited'`（有限公司）\| `'corporation'`（股份有限公司）\| `'studio'`（工作室）\| `'individual'`（個人） |
| `taxId` | text? | 統編（選填；工作室/個人可能沒有。若填則需通過 8 碼台灣統編檢核） |
| `plan` | enum | `'free'`（MVP 全免費） |
| `payoutDay` | int (1–31) \| null | 每月付款批次的付款日。1–31；31 等同月底（遇天數少的月份改在該月最後一天）。null = 關閉自動付款批次（支出不分組）。新公司預設 5。 |
| `createdAt` | timestamp | — |

**付款日規則（Company.payoutDay）**

- **用途**：決定 `Expense.plannedPayoutDate` 的 snapshot 值——建立／核准支出時用「登錄月的下個月 `payoutDay` 號」算一次寫入 `Expense.plannedPayoutDate`。
- **月底處理**：`payoutDay=31` 或 29/30 遇到該月天數不足時，退到該月最後一天。
- **變更語意（「只影響之後」）**：管理員改 `payoutDay` 時「不動」任何既有支出（含草稿、pending、paid、代墊款）的 `plannedPayoutDate` 與 `autoPlannedPayoutDate`。新規則只套用在之後新登錄 / 核准的支出；若要改既有 pending 支出的付款日，走單筆「調整付款日」(adjust-payout-date)。此設計避免管理員改一次設定就意外動到行政人員已排好的本月批次。
- **「改回自動排程」還原策略**：以 `Expense.autoPlannedPayoutDate` 為源頭還原 `plannedPayoutDate`，**不**重算快照。這確保同一筆支出的「自動值」是終身不變的屬性：即使中間經歷了手動調整＋改回，拿到的仍是登錄當下的原始自動值，不會因公司規則變動而漂移。
- **不需要歷史表**：因為 `plannedPayoutDate` 已 snapshot 到 Expense 本身，後端只需保存目前的 `payoutDay`；查詢「下一批」「逾期」直接讀欄位、可 index、不用 join。
- **變更紀錄（後端建議建）**：獨立於計算邏輯外的 audit 表，與 `payoutDay` 更新在同一 transaction 內寫入；供管理員追溯歷次變更使用。
  ```
  payout_day_change_log
  ├─ id
  ├─ company_id   uuid → Company
  ├─ changed_at   timestamp
  ├─ from_day     int | null
  ├─ to_day       int | null
  └─ changed_by   uuid → User
  ```
- **「本月」時區**：Prototype 用本機 `new Date()`；後端須統一公司時區（Taiwan/Taipei）為計算基準。

### 3.2 User（帳號）

MVP 系統只有兩種帳號：**超級管理員（1 個）** + **員工（≤10 個）**。

| 欄位 | 型別 | 說明 |
|---|---|---|

### 3.2.1 SignupToken（註冊 email 驗證 token）

管理員自助註冊流程專用。用戶輸入 email → 產 token → 寄驗證信 → 用戶點連結 →
帶 token 進註冊頁完成公司資料 + 密碼 → 消耗 token 建 Company + admin User。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | uuid | PK |
| `email` | text | 註冊信箱（小寫、trimmed） |
| `tokenDigest` | text (unique) | SHA256(raw token)；raw token 只在寄信時可見 |
| `provider` | enum | `'email'`（本地 email 驗證）\| `'google'`（Google OAuth，Stage D 才用到；預留） |
| `expiresAt` | timestamp | 過期時間（TTL = 30 分鐘） |
| `verifiedAt` | timestamp? | Step 2 GET verify 成功時填入；不代表 token 被消耗 |
| `consumedAt` | timestamp? | Step 3 complete 成功時填入；表示 token 已使用 |
| `createdAt` / `updatedAt` | timestamp | — |

**行為**：
- 每次 `generate_for(email)` 會把該 email 未消耗（`consumedAt IS NULL`）的舊 token 全部標為 `expiresAt = now`，避免用戶手上多封信互相干擾
- Step 2 GET verify 只驗證有效性、不消耗，用戶可重整註冊頁
- Step 3 complete 成功 → `consumedAt = now`；同一 token 不可再用

## 四、狀態機

### 4.1 Reimbursement.status（6 狀態）

沿用 ExpensePal 時期原設計。

```
                submit
       draft ──────────► in_review
         ▲                  │
         │ resubmit         ├──── approve ────► approved ──── pay ────► paid
         │                  │
         └──── rejected ◄───┘

         approved ──── void ────► voided   （撥款前可作廢）
```

| 狀態 | 中文 | 誰能操作 | 動作 |
|---|---|---|---|
| `draft` | 草稿 | 員工 | 只有員工能看；可編輯、submit、刪除 |
| `in_review` | 簽核中 | 超級管理員 | 可 approve、reject |
| `rejected` | 駁回 | 員工 | 員工可修改後 resubmit（回到 in_review） |
| `approved` | 已核銷（待撥款） | 超級管理員 | 系統已產生 Expense；可標記 paid；可 void |
| `paid` | 已發放 | — | 終態，不可變更 |
| `voided` | 已作廢 | — | 終態；只有 approved 狀態能 void |

**約束**：
- `draft` 狀態的 Reimbursement 只有申請人自己看得到；後台列表、tab 統計、儀表板一律排除
- `paid` 之後不可 void（會計已入帳）

### 4.2 Expense.payoutStatus（2 狀態）

```
pending ──── pay ────► paid
```

- 一般支出（`source='general'`）：建立時可直接 `paid`（若當下已付款）或 `pending`
- 代墊款轉來的（`source='reimbursement'`）：建立時 `pending`，撥款後 `paid`

### 4.3 刪除、還原、作廢、編輯與狀態切換

規則來源見 PRD 第 10、11、18 條，本表為動作對照。

| 動作 | 對象 | 條件 | 留紀錄 |
|---|---|---|---|
| 刪除（進入垃圾桶） | 支出、收入、固定收支範本、類別、帳戶 | 目前為待付款、待收款 | 稽核日誌 |
| 還原 | 垃圾桶內的支出、收入、固定收支範本、類別、帳戶 | 任何時候 | 稽核日誌 |
| 永久刪除 | 垃圾桶內的支出、收入、固定收支範本、類別、帳戶 | 使用者確認 | 稽核日誌保存完整內容，資料表移除該筆 |
| 作廢 | 代墊款 | 撥款前 | 簽核歷程；連動支出移入垃圾桶 |
| 取消作廢 | 代墊款 | 已作廢 | 歷程；連動支出還原 |
| 編輯 | 所有紀錄（含已付款、已收款） | 任何時候 | 變更前後內容 |
| 切換收付款狀態 | 支出、收入 | 任何時候，日期可填；切換時資料全部保留 | 從什麼改成什麼、日期、人、時間 |

## 五、資料流

### 5.1 一般支出登錄
```
行政 → ExpenseFormView
     ├─ 主表單（單筆）：憑證上傳 jpg/png → stub OCR 帶入 → 手動核對／填寫
     └─ 批次匯入 Dialog：PDF／Excel 上傳 → stub 解析 → 多筆預覽 → 逐筆確認
     → POST /expenses  { source: 'general', documentType, taxRate, vendor, ... }
     → 直接成立於統一支出列表
```

### 5.2 代墊款完整流程
```
員工 → 提交請款 → POST /reimbursements { status: 'draft' }
                → PATCH /reimbursements/:id/submit → in_review

超級管理員 → 審核清單 → PATCH /reimbursements/:id/approve
             ├─ Reimbursement.status = 'approved'
             ├─ CREATE Expense (source='reimbursement', sourceRefId=..., payoutStatus='pending')
             └─ Reimbursement.expenseId = 新 Expense.id
             
             或 → PATCH /reimbursements/:id/reject { reason }

超級管理員 → 撥款清單 → PATCH /expenses/:id/pay { payoutDate, method }
             ├─ Expense.payoutStatus = 'paid'
             └─ 若 source='reimbursement'：連動更新 Reimbursement.status = 'paid'
```

### 5.3 邀請員工流程
```
超級管理員 → 後台員工管理 → 「邀請」→ 填 email + name
          → CREATE Invitation { token, expiresAt: now + 3d }
          → 寄 email 含連結: https://.../invite/accept?token=xxx

被邀請人 → 點連結 → GET /invitations/:token → 驗證 token 有效
        → 顯示設密碼表單 → POST /invitations/:token/accept { password, name }
        → CREATE User (role='employee', companyId=from invitation)
        → Invitation.acceptedAt = now
        → 自動登入
```

## 六、核心查詢對照（對應 PRD/Sitemap）

> 所有列表與統計預設排除 `deletedAt` 有值的紀錄（垃圾桶）。

| 需求 | 查詢 |
|---|---|
| 待審佇列（後台簽核頁） | `Reimbursement WHERE companyId=X AND status IN ('in_review','rejected')` |
| 員工看自己的請款（前台儀表板） | `Reimbursement WHERE employeeId=me` |
| 統一支出列表（後台支出管理） | `Expense WHERE companyId=X ORDER BY date DESC`（可依 source 篩選） |
| 未結清代墊款 KPI（後台儀表板） | `SUM(amount) FROM Expense WHERE source='reimbursement' AND payoutStatus='pending'` |
| 本月支出總計 KPI | `SUM(amount) FROM Expense WHERE date IN this month`（含所有 source） |
| 本月支出筆數 KPI | `COUNT(*) FROM Expense WHERE date IN this month` |
| 近 12 月收支趨勢（儀表板大圖） | 收入 `GROUP BY month(date) FROM Income`、支出 `GROUP BY month(date) FROM Expense`，取近 12 個月，排除垃圾桶 |
| 類別預算執行率 | `SUM(Expense.amount) / Budget.amount WHERE category=X AND date IN period` |
| 本期損益（淨額） | `SUM(Income.amount) − SUM(Expense.amount)`，收入以 `date`（開立日）、支出以 `date` 落在期間內（垃圾桶內的紀錄不計入）|
| 本期現金收支 | 收款日落在期間內的收入合計 − 撥款日落在期間內的支出合計 |
| 年度逐月損益（損益報表） | 收入以 `GROUP BY month(date)`（開立日）、支出以 `GROUP BY month(date)`（發生日）彙總，期間為所選年度，共 12 欄；垃圾桶內的紀錄不計入 |
| 年度逐月現金流（現金流報表） | 收入以 `GROUP BY month(collectedAt)` 取已收款、支出以 `GROUP BY month(payoutDate)` 取已付款，期間為所選年度，共 12 欄；垃圾桶內的紀錄不計入 |
| 固定收支產生（每日檢查） | 找出 `lastGeneratedPeriod` 之後、已開始且未到期的範本，產生該期紀錄並更新 `lastGeneratedPeriod`；已刪除或已到期的範本不產生 |
| 待付款 KPI（儀表板） | `SUM(amount) FROM Expense WHERE payoutStatus='pending' AND deletedAt IS NULL`（含一般支出與代墊款） |
| 待收款 KPI | `SUM(amount) FROM Income WHERE collectionStatus='uncollected' AND deletedAt IS NULL` |
