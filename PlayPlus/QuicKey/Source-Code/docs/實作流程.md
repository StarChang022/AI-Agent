# QUICKEY 實作流程

> 目的：定義從前端 Prototype → 後端實作 → 前後端串接 → 官網上線的完整開發順序。
> 對應：`docs/產品規格文件.md`、`docs/sitemap.md`、`docs/資料模型.md`、`docs/技術選型.md`
> MVP 要出貨後端；先做完前端（元件／功能／API 契約）再實作後端，最後串接。

---

## 一、原則

1. **先前端完成 → 後端補齊 → 串接**：Stage A（前端）產出 API 契約後，Stage B（後端）照契約做，Stage C 把 Pinia store 內的 mock 換成 `fetch`。UI 元件 Stage C 幾乎不動。
2. **API 契約由前端主導**：Stage A 各 Phase 完成時，把該模組的 endpoint / request / response TS 型別放進 `frontend/src/api/`（一個模組一支檔）。這是後端的 contract 依據。
3. **一次一個 Phase**：做完一個 Phase 走一次 QA checklist，人工驗收通過再進下一個。
4. **由資料層往 UI**：先補 `types/domain.ts`、`mocks/*.json`、再改 Pinia store、最後動 UI。
5. **Stage A 不寫測試、Stage B 要寫**：前端 prototype 依 CLAUDE.md 慣例不寫測試；後端因涉及 DB migration 與交易一致性，建議做 integration test（Stage B 開始時再訂細節）。
6. **手機優先**：後台頁面必須手機能操作（見 `CLAUDE.md` 手機字級 14px 原則、`docs/dev/dev-style.md` 無障礙清單）。

## 四、命名調整說明（重要）

目前程式碼的 `Expense`/`ExpenseStatus`/`expenses.json`/`useExpenseStore` 對應的其實是新 PRD 的 **`Reimbursement`（代墊款請款）**。

新 PRD 是雙 model 架構（見 `docs/資料模型.md` §一）：
- `Reimbursement`：員工提交的請款單，走 6 狀態機
- `Expense`：已成立支出（含一般支出與代墊款轉來的），走 2 狀態機 `pending`/`paid`

**Phase 1 第一步**必須先做 rename，把現有 `Expense` 系列改名為 `Reimbursement`，之後再新增真正的 `Expense`。這個 rename 一次做完，不散在後續 Phase。

### Phase 4 — 代墊款 → 支出串接

**目的**：Reimbursement 核准時，由簽核者於 Dialog 決定是否**同步建立**一筆 `Expense`（`source='reimbursement'`），以 `Reimbursement.expenseId` ↔ `Expense.sourceRefId` 雙向連動。發放仍以 Reimbursement 為主體，若已成立 Expense 則連帶同步 `Expense.payoutStatus`。

**依賴**：Phase 1

**參考**：`docs/資料模型.md` §5.2；`openspec/changes/add-general-expense-module/design.md` Decisions 17／19；同 change `tasks.md` §10

**狀態**：✅ 已完成（併入 `add-general-expense-module` §10）。以下記錄實際實作與最初描述的差異，供將來閱讀者對照。

**實作要點**：

- `stores/reimbursements.ts` `approveCurrentStep(id, reviewerId, comment, options?)`：最後一 step 通過時，若 caller 傳入 `options.createExpense`（`vendor` / `categoryId` / `payoutStatus` / `tags`）就呼叫 `useExpenseStore.addFromReimbursement()`，把新 Expense.id 回填至 `reimbursement.expenseId`；未傳則只把 Reimbursement 標為 `approved`，Expense 之後另行補建
- `stores/reimbursements.ts` `createExpenseForApproved(id, adjustments, actorId)`：已核准但 `expenseId === null` 的補建入口，由 ReviewView 「已處理清單」「新增支出」按鈕呼叫
- `stores/expenses.ts` `addFromReimbursement(reimbursement, adjustments, reviewerId)`：固定填 `source='reimbursement'`、`sourceRefId=reimbursement.id`、`documentType='receipt'`、`taxRate='exempt_0'`；`vendor` 由 admin 於 Dialog 內填實際外部廠商（非員工姓名）
- `stores/expenses.ts` `markExpensePaidById(id)`：由 PayoutView 於 `markPaid` 成功後呼叫，同步 `Expense.payoutStatus='paid'`、`payoutDate=今日`
- `views/admin/ReviewView.vue`：`ApproveWithExpenseDialog` 承載「核准 + 補齊支出欄位」；「同時建立支出？」預設勾選（Decision 17）；已處理清單依 `expenseId` 顯示「已成立支出」/「未成立支出」chip 與「新增支出」按鈕（Decision 19）
- `views/admin/PayoutView.vue`：仍以 `reimbursements.value.filter(r => r.status === 'approved')` 為資料來源；`markPaid` 內 `if (target.expenseId)` guard 讓未成立 Expense 的 approved 代墊款可直接發放（2026-09-08 微調放寬，取代原本「必須先成立支出才能發放」的設計）
- `revertPaid` 反向同步 Expense：**MVP 不做**（tasks §10.D.3；Decision 8 定案）

**與最初 Phase 4 描述的差異**：

- 「核准時**系統自動** create Expense」→ 改為「reviewer 於 Dialog 選擇是否同時建立」（Decision 17）
- 「PayoutView 資料來源改成 `expenses.byStatus('pending')`」→ **不採用**；Payout 仍以 Reimbursement 為主體，Expense 為被動連動側
- 「approved 必然對應一筆 Expense」不變式 → 已撤回（Decision 19 允許 `expenseId === null` 的 approved 代墊款存在，並可直接發放）
- 「撥款走 `expenses` store，Reimbursement.status 隨之連動」→ 方向反過來：撥款走 `reimbursements` store，若有 Expense 才連動同步

**完成定義**：

- 簽核者於 Dialog 勾選「同時建立支出」通過後，該筆代墊款出現在「支出列表」（`pending`）與「發放清單」
- 未勾選者通過後只出現在「發放清單」；可於 ReviewView 已處理清單「新增支出」按鈕補建
- 發放頁標為已付款後：若已成立 Expense 則 `payoutStatus` 同步變 `paid`、`payoutDate=今日`；未成立則僅 Reimbursement.status 變 `paid`
- 只要有成立 Expense，`Reimbursement.expenseId` 與 `Expense.sourceRefId` 雙向對得起來

### 六.5 收尾（原 Phase 7）— Excel 匯入匯出 / Email 記錄 / OCR 假流程細節

**背景**：這批項目原本排在 Stage A Phase 7 做 stub / 假資料版；2026-09-22 決議延到 Stage B 執行——與後端 endpoint、OCR API、Email SMTP 一起做，避免前端先做一版假資料、後端接上後再重做一次的重工。

**執行時機**：Stage B 建議順序 item 7～10 施作時**同步**動這裡列出的前端檔案（Stage C 串接時再補剩下的 loading / error UX）。

**匯入匯出的前後端分工原則**：

| 場景 | 實作位置 | 理由 |
|---|---|---|
| Excel 匯出 | 前端用 `xlsx`／`exceljs` 直接產檔 | 資料量小、可控、不占後端資源 |
| Excel 匯入 | **前端解＋預覽（UX），後端負責最終驗證＋批次寫入** | 前端提供逐列修正 UX；後端須擋惡意繞過 UI 直接呼叫 API |
| PDF 解析（純文字） | 前端 `pdfjs-dist` 抽文字，或直接送後端 | 純文字 PDF 前端解很快，一頁一兩百 ms |
| PDF/圖片 OCR | **一律走後端**（第三方 OCR API，見技術選型） | `Tesseract.js` WASM ~10MB、手機端一頁中文 OCR 15–30 秒起跳，前端做不動 |

**效能 gating 策略**（前端側必做，避免手機瀏覽器凍住／OOM）：

- **檔案大小／列數門檻**：xlsx > 2MB 或試算後列數 > 3000 顯示「檔案過大，請用桌機匯入」並禁用送出。門檻常數放 `utils/import-limits.ts` 供未來調整
- **Web Worker**：xlsx 解析放進 worker（SheetJS 官方支援），避免主執行緒凍住 UI
- **手機端 UX**：偵測到手機 viewport 時，批次匯入 Dialog 直接顯示提示「建議改用桌機」，仍允許小檔案但預設收合
- **進度顯示**：解析、預覽、送出三段都給 progress state，不要只 spinner

**涉及檔案／工作**：

- **Excel 匯出**：`views/admin/ExpensesView.vue`、`views/admin/RecordsView.vue` 加匯出按鈕；`utils/export-xlsx.ts`（前端產檔）
- **Excel 匯入**：`components/BatchImportDialog.vue`（Phase 1 已建 stub）內接真解析；加 gating 檢查；Web Worker 版 `workers/xlsx-parse.worker.ts`；預覽通過後 `POST` 至後端 Excel 匯入 endpoint
- **PDF**：`BatchImportDialog.vue` PDF tab 純文字檔用 `pdfjs-dist` 抽文字後送後端；掃描檔／圖片直接送後端 OCR API
- **OCR UX**：辨識信心度低時顯示 warning、重複發票偵測（比對 vendor+date+amount，由後端提供 dedup check endpoint）
- **Email 通知記錄**：`stores/notifications.ts`（改讀後端寄件記錄）；Users 頁旁邊多一個「通知記錄」次頁可查

## 七、Stage C — 前後端串接

**方針**：一次一個 store，改完該 store 就手動 QA 一輪。

**步驟**：
1. 建 `frontend/src/api/client.ts`：`fetch` wrapper（token 注入、401 refresh、error normalize）
2. 依 Stage A 契約檔一支一支實作 API function
3. Pinia store 內原本操作 `expenses.value` 陣列的地方，改成 `await api.xxx()`
4. localStorage 只保留 auth token；業務資料改讀 server
5. 空狀態 / loading / error UI 補齊（Stage A 已預留 skeleton 位置）
6. Feature flag：在 auth store 開個 `useMockData` boolean 供逐步切換

**風險點**：
- 樂觀更新 vs. 悲觀更新的取捨（本專案傾向悲觀，一致性優先）
- 大檔案上傳（憑證）進度顯示與失敗重試

## 八、Stage D — 官網 + 註冊

### 8.1 Repo 決策：**獨立 repo**

`quickey-landing` 與本 repo 分開（CLAUDE.md 原本規劃）。理由：

- **團隊邊界對齊**：Miki 負責行銷 UI、Peggy 負責 app；分 repo 各自 CI/CD 不互相 block
- **技術棧會分岔**：官網要 SEO + 部落格（傾向 Nuxt 或 Astro 靜態生成）；Quickey app 是 PWA + 有登入態，技術重心不同
- **註冊流程仍能無縫**：見下節

### 8.2 註冊流程：註冊表單放在 Quickey app

官網不做註冊表單，只做 CTA。使用者點官網「開始免費試用」→ 跳到 `app.quickey.com/register`。這樣就沒有 SSO / cookie 跨域問題。

**Quickey app 側要做**：
- 新 `views/RegisterView.vue`（public route `/register`）：Email + 密碼 + 公司名稱（選填）
- `stores/auth.ts` 加 `register(email, password, companyName?)` action
- `frontend/src/api/auth.ts`：加 `POST /auth/register` 契約
- 註冊成功 → 自動登入 → 導向 admin dashboard → 觸發 Phase 6 的 Onboarding wizard

**quickey-landing 側要做**：
- 一頁式 landing（Banner / 產品特色 / 常見問題 / 聯絡我們 / 隱私權 / 服務條款）
- 部落格
- 所有 CTA 按鈕 `<a href="https://app.quickey.com/register">開始免費試用</a>`

**部署**：
- 官網：`quickey.com`
- App：`app.quickey.com`
- 兩者可各自部署，發布不互相牽動

**時程**：可與 Stage B 平行進行（Miki 做官網、Peggy 做後端）。
