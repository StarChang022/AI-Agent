# 產品情境

## 前置作業

基礎資料庫與素材庫建置。

在系統啟用前，資料庫已預先建立餐飲品項的基本資料（品項名稱、POS 系統對應 ID、分類、食材成本與毛利級距），並由品牌方上傳各品項的多角度高解析度照片、各門市環境照與品牌視覺套版規範。

1. **餐飲品項基本資料**:
	- 品項名稱
	- POS 系統對應 ID（對應 POS 系統料號）
	- 分類（如湯底、肉品、海鮮等）
	- 食材成本
	- 毛利級距

2. **品牌多媒體素材與規範**:
	- 餐飲品項照片（各品項之多角度、高解析度照片）
	- 門市環境照（各分店現場環境空間照）

## 每日 23:00 整合數據

系統每日 23:00 準時發動定時任務，向外部系統批次撈取當日運作資料。

1. **Eats365 POS 系統**:
	全門市當日結帳資料、各品項銷量、時段營收、客單價、即期與安全食材庫存水位、POS 連線狀態。
	- 全門市當日結帳資料
	- 各品項銷售數量與排行
	- 時段營收分佈
	- 客單價
	- 食材庫存水位（包含「即期庫存」與「安全庫存」狀態）
	- POS 連線狀態（作為斷線異常風控依據）

2. **Google Maps**:
	透過 Google Business Profile API 批次讀取各分店當日新增之所有評論與星等。
	- 當日新增評論內文
	- 當日新增評分與星等（1~5 星）

3. **inline 訂位系統**:
	撈取各門市明日各餐期（午餐、晚餐、宵夜）各時段的已訂桌數與剩餘桌型。
	- 各時段已訂桌數
	- 各時段剩餘桌型與名額

4. **外部氣象 API**:
	撈取各門市所在行政區明日各餐期的降雨機率、氣溫預測與體感溫度。
	- 明日各餐期降雨機率
	- 氣溫預測
	- 體感溫度

```
[每日 23:00 一站式撈取資料]
 ├─ POS 營運與庫存數據
 ├─ Google Maps 評論與星等
 ├─ inline 明日預約率
 └─ 各門市氣象預報
       │
       ├───> [情境 1] 品牌餐飲日誌
       │       ├─ 正常運作：生成草稿 ──> 管理者審核（隔日 05:00 逾時自動發布）
       │       └─ 異常分支 [情境 1-1]：偵測 1~2 星負評/斷線 ──> LINE 告警熔斷（逾時不執行）
       │
       └───> [情境 2] 空桌促銷引擎

                                                                        └─> 顧客訂位帶碼 ──> POS 核銷

```

## 情境 1 ： 品牌餐飲日誌

系統自動從撈取到的數據判斷文案話題，例如今日被加點頻率最高的單品（如點麻辣鍋的客人有 70% 加點老油條）、特定時段高翻桌率的反差數據（例如平日晚上翻桌達 2.8 輪）、好評關鍵字交叉比對（將當日 Google Maps 4星5星評論提到的菜色作為顧客真實證言）。

1. **亮點萃取與圖卡合成**
	AI 分析全門市數據，找出最具話題性或反差感的亮點，自動至資料庫調用該品項照片，套用品牌模板生成 Instagram 雙圖/多圖輪播圖卡，並同步產出 Instagram / Facebook / Threads 差異化文案草稿。
2. **推播審核（23:10）**
	系統透過 LINE 官方帳號推播審核卡片給品牌管理者，提供「確定發布／手動修改／AI重寫／停止」4個選項。
3. **發布機制**
	- **確定發布** : 點擊後系統立即或排程發布至社群平台。
	- **手動修改** : 點擊後手動修改文案，修改完畢立即或排程發布至社群平台。
	- **AI重寫** : 點擊後再次讓 AI 重寫文案。
	- **停止** : 點擊後停止此次發布。
	- 若管理者於隔日 05:00 前未進行任何操作，系統判定為默許，自動於 05:00 自動發布至社群。

## 情境 1-1 ： 評論異常警報（異常分支）

1. **異常偵測**
	系統在 23:00 數據分析階段，若偵測到特定門市當日從 Google Maps 收到1星或2星負評，或特定門市 POS 因網路中斷未回傳資料。
2. **自動隔離機制**
	系統立即將該異常分店從當日「品牌餐飲日誌」的統計樣本與宣傳亮點中剔除，僅執行其餘營運正常的門市。
3. **即時警報與審核鎖定**
	- 系統透過 LINE 發送高優先級告警訊息給督導與管理者，標註「門市名稱、負評星等、評論內文、關聯餐期」，管理者自行決定是否執行後續步驟。
	- 若管理者於隔日 05:00 前未決定如何執行，系統維持隔離保護。

## 情境 2 ： 空桌促銷引擎

1. **空桌與庫存匹配（23:00）**
	- 系統檢查各門市明日 inline 訂位數據，篩選出低於警戒值的門市。
	- 交叉比對該門市的 POS 庫存，挑選庫存高於安全水位且具吸引力的高毛利單品作為贈品（如鮮甜蛤蜊）。
	- 結合明日氣象（如降雨機率 70%、低溫 16 度），決定推播切入點。
2. **優惠券生成與審核（23:10）**
	- 系統自動建立該門市專屬促銷代碼（例如 00520），並設定限量組數（如 10 組）及適用時段。
	- 生成 Instagram / Facebook / Threads 促銷文案與優惠時段圖卡，推播至管理者審核。
	- 審核邏輯同品牌餐飲日誌，管理者可選擇「確定發布／手動修改／AI重寫／停止」；若隔日 05:00 前未審核則由系統自動排程發布。
3. **社群領券與訂位**
	- 顧客在社群看到貼文，點擊分店專屬訂位連結。
	- 進入 inline 訂位時，系統自動在訂位備註寫入「優惠碼 00520」，並透過簡訊或 Email 將訂位確認及優惠碼發送給顧客。
	- 當名額達上限（10 組）時，專屬連結自動轉為一般無優惠訂位頁面。
4. **門市現場核銷**
	- 隔日顧客到店入座，口頭報出優惠碼或出示簡訊。
	- 外場店員在 POS 系統輸入該優惠碼，系統即時驗證「適用分店／符合入場時段」。
	- POS 自動帶入「贈品」或「折價」，並將該筆優惠碼狀態註銷，杜絕重覆使用。

# 使用者故事

從管理者、一線人員及顧客三個角色思考。

## 角色 A ： 品牌管理者 / 營運總監

負責決策、風控與營收的角色。

- **批次審核與逾時自動託管** : 身為品牌管理者，我希望系統每天 23:00 自動產出餐飲日誌與促銷草稿並透過 LINE 傳送給我，讓我能快速選擇發布、修改或由 AI 重寫，且在我不小心睡著或未處理時於 05:00 自動發布，以便在保有控制權的同時落實行銷自動化。
- **負評自動熔斷保護** : 身為品牌管理者，我希望當分店出現 1~2 星 Google 負評或系統斷線時，系統能自動將該店排除於宣傳名單外並發出告警，且在未經我手動確認前絕不自動發布該店內容，以避免在客訴爭議期間引發公關危機。
- **動態消化剩餘桌位與庫存** : 身為品牌管理者，我希望系統能針對明日訂位率落後的門市自動挑選充足庫存的食材發起限時促銷，以便在維持合理食材成本的前提下，有效拉抬離峰時段的翻桌率。

## 角色 B ： 分店現場人員

店長或服務人員。

- **即時掌握客訴事件** : 身為門市店長，我希望當本店收到 Google 嚴重負評時能即時收到通知，以便在隔日營業前立即調閱監視器、釐清出餐狀況並向顧客致歉處理。
- **極簡 POS 核銷流程** : 身為外場服務人員，我希望客人口頭報出優惠碼時，我只需要在 POS 機輸入代碼就能自動帶入 0 元贈品並完成扣抵，不需手動修改帳單金額或向主管請示折扣權限。
- **控制促銷桌數防爆單** : 身為內外場人員，我希望系統發出的優惠碼嚴格受限於設定組數（如 10 組），避免大量兌換造成廚房備料不及與現場出餐混亂。

## 角色 C ： 終端消費者

想要吃火鍋的消費者或追蹤餐飲品牌社群的顧客。

- **無痛獲取專屬優惠** : 身為常客或潛在顧客，我希望在社群看到離峰優惠貼文時，點擊連結就能完成訂位並自動在備註帶入優惠碼，不必在到店時拿出手機向店員爭取贈品，降低核銷的麻煩。
- **取得明確憑證與提醒** : 身為訂位顧客，我希望訂位完成後能透過 Email 或簡訊收到包含優惠碼的明確憑證，以便在用餐當天能輕鬆出示給店家確認。

# 架構文件

完整撰寫「Eats365 POS 介接規格」、「LINE 官方帳號與 Messaging API 介接規格」、「AI 調度規格」、「核心資料流與狀態機」以及「基礎資料庫綱要設計」的完整系統架構文件。

## 1. 系統總覽

本系統以後端應用伺服器（Backend Engine）為運算與排程核心，整合 Eats365 POS 營運數據、inline 訂位、Google Maps 評論及氣象資訊。系統於每日 23:00 彙整多店數據並執行風控篩選，透過 API 調用大語言模型（LLM API）產出結構化洞察與社群文案，結合影像合成模組產出圖卡，最後經由 LINE 審核機制與 Meta Graph API 達成全通路發布與優惠核銷閉環。

## 2. 系統架構分層

### 2.1 外部整合層

- **Eats365 POS 系統 API** : 基於 RESTful 架構與 Webhook 事件機制，透過 OAuth 2.0 憑證對接 Eats365 Partner Portal。負責撈取各門市關帳數據、品項銷量與加點排行、食材在架與售罄庫存，並提供自訂促銷代碼註冊與現場核銷驗證端點。
- **inline 訂位系統** : 讀取明日各餐期預約率與剩餘桌型，並提供訂位備註寫入介面（支援企業 API 介接模式，或透過專屬社群 URL Deeplink 轉導帶碼搭配後台/Eats365 桌況之零 API 費用模式）。
- **Google Business Profile (GBP) API** : 批次讀取旗下所有分店當日新增評論與星等，確保全量讀取以支援 1~2 星負評即時熔斷（具備第三方商業評論抓取 API 作為審核期備援）。
- **外部氣象 API** : 依各門市經緯度查詢明日降雨機率與氣溫變化。
- **LLM API** : 調用雲端大語言模型（如 Gemini API），以 Structured Outputs（JSON 模式）輸出商業洞察與平台適配文案。
- **LINE Messaging API (LINE 官方帳號)** : 作為營運決策與審核中樞，以 Messaging API 與品牌管理者進行雙向通訊。利用 Flex Message 推播結構化審核卡片與緊急負評熔斷告警，並透過 Webhook 接收 Postback 操作指令，同時藉由免費用量的 Reply API 達成即時操作回饋。
- **Meta Graph API** : 對接 Instagram Content Publishing API、Threads API 與 Facebook Pages API，執行多圖輪播與圖文發布。

### 2.2 核心邏輯層

- **排程控制器 (Cron Scheduler)** : 固定於 23:00 觸發資料擷取任務，並於 05:00 掃描逾時未審核任務執行自動發布。
- **異常風控引擎 (Risk Management Engine)** : 後端以規則為基礎（Rule-based）檢查當日評論與連線狀態。若觸發 1–2 星評論或 Eats365 資料斷線/未關帳，將該分店標記為 `QUARANTINED`，直接阻斷其納入當晚宣傳。
- **Prompt 上下文組裝器 (Context Assembler)** : 將正規化後的營運數據、食材安全庫存與品牌人設組裝為標準化 JSON Payload 發送至 LLM。
- **動態影像合成器 (Image Compositor)** : 調用數位資產庫素材，套用排版模板與文字壓印，產出符合 IG 尺寸（1:1 / 4:5）的發布圖卡。
- **優惠碼配發引擎 (Coupon Engine)** : 生成具時效性、綁定分店與時段的單次唯一核銷代碼（如 `00520`），寫入資料庫並同步向 Eats365 建立促銷與優惠券池。

### 2.3 互動與審核層

- **LINE Webhook Handler** : 接收 LINE 官方伺服器推送之 Postback 事件，強制以 Channel Secret 進行 HMAC-SHA256 簽章比對（`x-line-signature`）。採非同步處理並於 5 秒內回應 200 OK，即刻更新任務狀態機並以 `replyToken` 送出操作確認。
- **Eats365 Webhook Handler** : 監聽門市打烊關帳 (`shift.closed`) 與訂單結帳核銷 (`order.completed` / `order.closed`) 事件，驅動排程判斷與優惠碼狀態回寫。

### 2.4 資料儲存層

- **關聯式資料庫 (RDBMS - PostgreSQL / MySQL)** : 儲存門市設定、警戒值門檻、每日營運快照、促銷優惠碼狀態機、審核紀錄與發布紀錄。
- **數位資產管理庫 (DAM - AWS S3 / Cloud Storage)** : 儲存餐飲品項高解析圖檔、圖卡模板字型、合成後的發布圖檔。

## 3. Eats365 POS 介接規格與端點調度

### 3.1 認證機制與授權規範 (OAuth 2.0)

Eats365 採用標準的 OAuth 2.0 機制搭配 API 憑據管理：

- **認證方式** : 採用 Bearer Token 形式放置於 HTTP Header。
  ```http
  Authorization: Bearer <access_token>
  Content-Type: application/json
  X-Eats365-Merchant-Id: <merchant_id>
  ```
- **Token 生命週期** :
  - **Access Token** : 有效期數小時至 24 小時。
  - **Refresh Token** : 後端於背景定期自動換發，確保每日 23:00 定時排程具備長期連線憑證。
- **多門市授權層級 (Multi-Store Scoping)** :
  系統取得品牌組織（Merchant/Organization）層級憑證，呼叫端點時於 Header 或 Query Parameter 帶入分店代碼（`store_id`），即可單點切換並存取不同門市數據。

### 3.2 核心功能模組與端點劃分

- **營運報表與交易數據模組 (Sales & Transaction API)** :
  - **日結關帳報表 (`GET /v1/reports/daily_sales`)** : 傳入 `store_id` 與 `date` (YYYY-MM-DD)，取得全日淨營收、總單數、內用人數（Covers/Guest Count）、客單價（AOV）、時段別營收分布（小時為單位）、關帳結算時間。
  - **訂單明細與品項排行 (`GET /v1/orders` 或 `GET /v1/reports/item_sales`)** : 取得當日品項代碼 (`item_id`)、品項名稱、銷售總份數 (`quantity`)、火鍋加點與客製選單細項 (`modifiers`，如辣度調整、麻辣湯底加點老油條)、折扣折抵金額 (`discount_amount`)。
- **菜單與食材庫存模組 (Menu & Inventory API)** :
  - **品項清單與分類 (`GET /v1/menu/items`)** : 取得全店菜單品項、價格、成本級距與分類（肉品、海鮮、湯底）。
  - **庫存水位查詢 (`GET /v1/inventory/stocks`)** : 查詢特定品項的當前在架剩餘數量（Remaining Stock）。
  - **售罄標記安全防線 (`GET /v1/menu/items/out_of_stock`)** : 檢查現場外場是否將贈品候選單品（如鮮甜蛤蜊）設為停售（86 List / Out of Stock），作為促銷白名單的安全防線。
- **行銷活動與優惠碼核銷模組 (Promotions & Loyalty API)** :
  - **建立自訂促銷規則 (`POST /v1/promotions`)** : 傳入促銷名稱、生效日期區間、指定適用門市陣列、贈送商品 ID、適用用餐型態（限定內用）。
  - **自訂券碼核銷 (`POST /v1/vouchers/verify` 或 `POST /v1/orders/{order_id}/apply_discount`)** : 預先註冊促銷代碼池（Voucher Codes），收銀機輸入優惠碼時由 POS 終端發起校驗，回傳 200 OK 則直接將指定品項改為 0 元或折抵對應金額。
- **即時事件監聽 (Webhooks)** :
  - `shift.closed` : 門市正式執行打烊關帳時觸發，可作為系統在 23:00 前提早判定各店結帳狀態的事件驅動指標。
  - `order.completed` / `order.closed` : 訂單完成結帳時推送，包含該筆訂單所使用的優惠券代碼，用於即時回寫優惠碼核銷狀態為 `REDEEMED`。

### 3.3 開發規範、環境限制與錯誤處理

- **Sandbox 測試環境** : Eats365 提供獨立 Sandbox 網址與測試帳號，後台可直接模擬虛擬門市、建立虛擬菜單，並提供模擬 POS Client 進行下單與結帳驗證。
- **分頁與數據限制 (Pagination)** : 列表類端點採標準分頁參數（`page=1&limit=50` 或 `offset/limit`），撈取大量訂單明細時以小時為區間批次拉取，避免單一 Request 逾時。
- **呼叫頻率限制 (Rate Limits)** : 門市 API 的 Request 限制約落在每分鐘 60 至 120 次。系統每日 23:00 採批次排程拉取 3–10 間門市，查詢量遠低於頻率上限，不會觸發 HTTP 429 Too Many Requests。
- **時間戳記與時區** : 所有時間欄位一律採用 ISO 8601 格式（包含時區位移，例如 `2026-10-19T22:30:00+08:00`），避免跨時區排程判斷失誤。

### 3.4 每日排程與 Eats365 端點調度對應

每日 23:00 系統背景作業與 Eats365 端點的具體呼叫鏈路如下：

1. **驗證關帳狀態** : 呼叫 `GET /v1/stores` 讀取 3–10 間門市清單，並檢查各店最後一筆關帳紀錄或監聽 `shift.closed` 事件。
2. **拉取品項數據** : 對每間正常分店呼叫 `GET /v1/reports/item_sales?store_id={id}&date={today}`，取得銷量第一的湯底與最高加點率單品。
3. **確認贈品庫存** : 針對訂位低於警戒值的門市，呼叫 `GET /v1/inventory/stocks?store_id={id}&item_id={clam_id}` 確認備料數量大於 10 份，並交叉比對 `GET /v1/menu/items/out_of_stock` 確認未被現場設為停售。
4. **註冊明日代碼** : 呼叫 `POST /v1/promotions`（或 `POST /v1/promotions/coupons`），預先向 Eats365 寫入 10 組明日 17:30–18:30 有效的獨立核銷碼。

## 4. LINE 官方帳號與 Messaging API 介接規格

LINE Messaging API 是本系統與連鎖品牌營運團隊（品牌總監、營運督導、門市店長）間的即時通訊與行動決策中樞，負責審核卡片推播、即時異常告警與操作指令接收。

### 4.1 帳號憑證與身分驗證 (Credentials & Authentication)

在 LINE Developers Console 建立「Messaging API Channel」並綁定品牌 LINE 官方帳號後，系統維護以下憑證與目標參數：

- **頻道憑證 (Channel Credentials)** :
  - **Channel ID** : Messaging API Channel 唯一識別碼。
  - **Channel Secret** : 用於 Webhook 請求的雜湊簽章比對（HMAC-SHA256），防止偽冒請求。
  - **Channel Access Token** :
    - *長期 Token（Long-lived Token）* : 後台手動生成，無到期日，適用初期開發與測試。
    - *短效動態 Token（OAuth 2.0 v2.1）* : 呼叫 `POST https://api.line.me/v2/oauth/accessToken` 動態換發（效期 30 天），生產環境採背景定期換發機制以維護資安強度。
- **HTTP Header 呼叫規範** :
  ```http
  Authorization: Bearer {CHANNEL_ACCESS_TOKEN}
  Content-Type: application/json
  ```
- **目標對象識別 (User Identification)** :
  推播目標使用 LINE 原生 `userId`（以 `U` 開頭之 33 碼專屬字串，非公開 LINE ID）或特定內部群組 `groupId`。

### 4.2 訊息發送機制與 API 端點 (Outbound Messaging)

系統將對外發送訊息劃分為「主動推播（Push/Multicast）」與「被動即時回覆（Reply）」：

- **主動推播 API (`POST /v2/bot/message/push` / `/multicast`)** :
  - **呼叫時機** : 每日 23:10 產出日誌與促銷草稿時，或偵測到 1–2 星負評與 POS 斷線時主動告警。
  - **單一推播 (`POST /v2/bot/message/push`)** : 傳入管理者 `userId` 或 `groupId`，`messages` 陣列上限 5 則訊息物件。
  - **多人群發 (`POST /v2/bot/message/multicast`)** : 若需同時發送給多位決策者（如品牌總監、營運督導、當店店長），在 `to` 陣列傳入多位 `userId`（上限 500 人），單次呼叫即可完成全體通知，避免重複多次呼叫推播端點。
- **被動即時回覆 API (`POST /v2/bot/message/reply`)** :
  - **呼叫時機** : 管理者點擊卡片動作按鈕後，系統立即給予操作確認與執行反饋。
  - **核心欄位** : 帶入 Webhook 事件內之單次有效憑證 `replyToken`（時效約 1 分鐘）。
  - **成本效益** : **Reply 訊息完全免費**，不佔用 LINE 官方帳號的每月推播則數額度。

### 4.3 Webhook 接收與安全驗證 (Inbound & Security)

管理者於 LINE 聊天室點選按鈕時，LINE 伺服器即時向後端發送 HTTP POST Webhook。

- **簽章防偽驗證（強制資安要求）** :
  後端收到請求後，必須比對 Header 中的 `x-line-signature`：
  1. 取出 Webhook Request 的完整原始字串（Raw Request Body）。
  2. 使用 `Channel Secret` 作為密鑰，以 `HMAC-SHA256` 演算法計算出雜湊值。
  3. 將雜湊值轉為 Base64 字串，與 Header 的 `x-line-signature` 比對；若不符則直接回應 `401 Unauthorized` 終止處理。
- **關鍵事件型態：Postback Event** :
  管理者點擊審核卡片按鈕時觸發 `postback` 事件：
  ```json
  {
    "events": [
      {
        "type": "postback",
        "replyToken": "nHuyWiB7yP5Zw52FIkcQobQuGDXCTA",
        "source": {
          "userId": "U4af4980629...",
          "type": "user"
        },
        "timestamp": 1774026600000,
        "postback": {
          "data": "action=publish&task_id=TASK_20261019_01&task_type=JOURNAL"
        }
      }
    ]
  }
  ```
  後端解析 `postback.data` 參數，即可精確分流五大操作指令：「確定發布 (`action=publish`)」、「手動修改 (`action=edit`)」、「AI重寫 (`action=rewrite`)」、「停止 (`action=stop`)」或「解除隔離 (`action=override_quarantine`)」。
- **5 秒 Timeout 與非同步處理規範** :
  LINE 官方要求 Webhook 必須於 **5 秒內**回傳 HTTP `200 OK`，逾期將觸發重送機制。後端設計採非同步（Async）派工：驗證簽章無誤後立即回傳 `200 OK`，並於背景執行狀態機轉換與社群 API 發布，同時調用 `replyToken` 回覆執行進度。

### 4.4 審核卡片 UI 規格：Flex Message (UI Specification)

推播審核卡片採用以 CSS Flexbox 為排版架構的結構化 JSON（Flex Message），具備高度視覺層次與互動能力：

- **容器結構 (Container Hierarchy)** :
  - **`Bubble` 單卡片** :
    - `header` : 顯示門市名稱、任務類別（日誌/促銷）與日期標籤。
    - `hero` : 嵌入影像合成器產出之圖卡縮圖（支援 1:1 或 4:5 比例）。
    - `body` : 呈現 LLM 產出之文案摘要、反差數據（如「麻辣鍋加點老油條 70%」）或促銷庫存時段。
    - `footer` : 配置操作按鈕群。
  - **`Carousel` 多卡輪播容器** :
    最多可並排容納 12 個 Bubble。本系統每晚 23:10 可將「品牌餐飲日誌」與「各分店空桌促銷草稿」組合為單一 Carousel 訊息發送，讓管理者左右滑動一站式完成審核。
- **按鈕動作規範 (Actions)** :
  卡片按鈕一律綁定 `postback` 型別：
  - `type` : `"postback"`
  - `label` : 按鈕顯示文字（如「確定發布」、「手動修改」、「AI重寫」、「停止」）。
  - `data` : 傳入後端隱藏參數（如 `action=publish&task_id=TASK_01`）。
  - `displayText` : 使用者點擊後於對話框帶出一行友善提示（如「已確認發布餐飲日誌」）。

### 4.5 費用、配額與頻率評估 (Cost & Quotas)

- **訊息配額與計費評估** :
  - 台灣 LINE 官方帳號低用量（輕度）方案每月提供 200 則免費主動推播。
  - 僅調用 `push` 與 `multicast` 時扣除額度；點選按鈕後觸發的 `reply` 訊息完全免費。
  - 系統每晚 23:10 僅發送 1 則 Carousel 審核卡片給 1~3 位特定營運主管，全月僅消耗 30~90 則推播，完全涵蓋在免費額度或最低月租內，營運成本極低。
- **頻率限制 (Rate Limits)** :
  Messaging API 承受上限達每秒 2,000 個請求（RPS），品牌審核推播使用量遠低於限制門檻。

### 4.6 審核互動鏈路對應 (End-to-End Flow)

1. **23:10 推播** : 後端將 AI 生成之多平台文案與圖卡組裝為 Flex Message Carousel，呼叫 `POST /v2/bot/message/push`（或 `multicast`）送達管理者手機。
2. **主管決策** : 管理者檢視卡片，點選「確定發布」按鈕。
3. **Webhook 簽章驗證** : 後端接收 `postback` 事件，完成 `HMAC-SHA256` 簽章核驗，確認請求合法性。
4. **即時免費回饋** : 後端取出 `replyToken`，呼叫 `POST /v2/bot/message/reply` 送出「已確認！系統正在排程發布至 IG、FB 與 Threads...」。
5. **狀態機流轉與發布** : 後端將 `approval_tasks` 狀態變更為 `PUBLISHED`，並呼叫 Meta Graph API 完成全通路排程發布。

## 6. 核心資料流與狀態機

### 6.1 品牌餐飲日誌狀態流轉

```
[23:00 排程觸發] ──> [FETCHING: 擷取 Eats365 / 評論]
                            │
       ┌────────────────────┴────────────────────┐
       ▼                                         ▼
[無負評: READY_FOR_AI]                   [偵測 1-2 星/斷線: QUARANTINED]
       │                                         │
       ▼                                         ├─> LINE Flex Message 緊急告警
[AI 生成中: GENERATING]                          │
       │                                         ▼
       ▼                                  [待手動解除: AWAITING_OVERRIDE]
[LINE 推播審核: PENDING_APPROVAL]                 │
       │                                         ├── 05:00 前 LINE 手動解除 ──> 併入日誌發布
       ├── 主管點擊「發出」(Postback) ──> [PUBLISHED]  └── 05:00 未動作 ────────────> [AUTO_CANCELLED]
       └── 05:00 逾時未處理 ───────────> [AUTO_PUBLISHED]
```

- `FETCHING` : 系統正在向 Eats365 API 與 Google GBP API 撈取資料。
- `QUARANTINED` : 分店當日出現 1–2 星評論或 Eats365 網路中斷未回傳關帳資料，系統鎖定該店資料，不送入 AI 生成名單。
- `READY_FOR_AI` : 資料檢查正常，準備組裝 Prompt。
- `GENERATING` : 呼叫 LLM API 並調用影像合成器產出圖卡。
- `PENDING_APPROVAL` : 素材完成，以 LINE Flex Message 推播至管理者帳號供審核。
- `PUBLISHED` : 管理者於 05:00 前點選發布（觸發 Postback Webhook），系統即時呼叫 Meta API 發布至 IG、Threads、FB。
- `AUTO_PUBLISHED` : 管理者至 05:00 皆未操作，系統判定為默許發布。
- `AUTO_CANCELLED` : 處於隔離狀態的分店至 05:00 仍未解除鎖定，系統終止發布以保護品牌。

### 6.2 空桌促銷與核銷閉環狀態機

```
[23:00 掃描明日訂位率]
          │
          ▼
[符合門檻: 低於預警值且庫存安全] ──> [Eats365 註冊限量代碼: ACTIVE]
                                           │
                                           ▼
                                 [發布至社群 + 附帶預約短網址]
                                           │
                                           ▼
                                 [顧客點擊 inline 訂位] ──> [CLAIMED / 綁定預約]
                                                                │
                                   ┌────────────────────────────┴───────────────────────────┐
                                   ▼                                                        ▼
                    [顧客到店: POS 輸入核銷/Webhook 回傳]                       [逾時未到店 / 違規]
                                   │                                                        │
                                   ▼                                                        ▼
                              [REDEEMED]                                                [EXPIRED]
```

- `ACTIVE` : 代碼已建立並同步至 Eats365 促銷池，發布於社群，名額未滿，可供顧客預約鎖定。
- `CLAIMED` : 顧客完成 inline 訂位，該代碼已綁定特定預約編號與手機末三碼。
- `REDEEMED` : 門市人員於 POS 機輸入代碼完成驗證（或觸發 Eats365 `order.completed` Webhook），系統帶入 0 元贈品並註銷代碼。
- `EXPIRED` : 預約時段已過或顧客 No-show，代碼自動作廢。

- `inline_booking_id` (VARCHAR) : 綁定之 inline 訂位編號。
- `customer_phone_last3` (VARCHAR) : 顧客手機末三碼。
- `status` (VARCHAR) : 狀態（`ACTIVE`, `CLAIMED`, `REDEEMED`, `EXPIRED`）。
- `redeemed_at` (TIMESTAMP) : POS 現場核銷時間。
- `action_logs`（系統操作與稽核紀錄表）
- `id` (BIGINT, PK, Auto-increment)
- `event_type` (VARCHAR) : 事件類型（如 `QUARANTINE_TRIGGERED`, `POS_REDEEM_SUCCESS`, `EATS365_WEBHOOK_RECEIVED`, `LINE_POSTBACK_RECEIVED`, `LINE_REPLY_SUCCESS`）。
- `payload` (JSONB) : 事件請求與回應完整內容。
- `created_at` (TIMESTAMP) : 建立時間。

## 數據採集

- **Eats365 營運數據介接**（系統）
  批次擷取全門市每日結帳營運數據。
  - OAuth 2.0 授權認證與 Access/Refresh Token 自動定期換發。
  - 支援品牌組織憑證與多門市切換（Multi-Store Scoping）。
  - 撈取全門市日結關帳報表（淨營收、總單數、內用人數、客單價、小時營收分布）。
  - 撈取品項銷量排行與訂單加點細項（modifiers，如麻辣鍋加點老油條）。

- **Eats365 食材庫存與售罄監控**（系統）
  確認贈品備料與防呆停售狀態。

  - 交叉比對現場售罄停售清單（86 List / out_of_stock），避免贈品缺貨引發客訴。

- **Google Maps 評論批次擷取**（系統）
  批次讀取全門市 Google 商家最新顧客回饋。
  - 透過 Google Business Profile API 撈取當日新增之所有評論內文。
  - 擷取評分星等（1~5 星）與發布時間戳記。

- **inline 訂位預約數據介接**（系統）
  讀取各門市明日預約負載與桌位結構。
  - 撈取明日各餐期（午餐、晚餐、宵夜）已訂桌數與剩餘桌型。
  - 計算明日各時段預估訂位率，精確鎖定低於警戒門檻時段。

- **外部氣象資訊即時介接**（系統）
  精準掌握門市微氣候，作為文案與促銷觸發依據。
  - 依各分店經緯度查詢明日各餐期降雨機率。
  - 撈取明日預測氣溫與體感溫度數據。

  - 遇到不可抗力失敗時自動降級切換至本地靜態文案模板，確保 23:10 前準時推播審核卡片。

## 一、 確定免 API 費用的服務項目

以下 3 項為官方公開開放或無調用規費的項目，**6 個月 API 費用為 0 元**：

## 二、 具商務條件與審核門檻之服務項目（inline 與 Google Maps）

這兩項在業界實務上**存在商務門檻或審核條件**，並非無條件完全免費，需依品牌合約情境評估：

### 1. inline 訂位系統（商務介接門檻）
- **功能需求**：每日 23:00 自動撈取明日各餐期之已訂桌數與剩餘桌型。
- **實務現況**：
  - inline 官方**未開放免費自助 Open API**，一般標準訂位合約不含 API 存取權限。
  - 店家欲開通後端 API 拋接資料，通常須升級至**企業專案（Enterprise Plan）**或向業務增購**「系統/POS 介接模組」**。
- **費用評估與替代方案**：
  - **情境 1（品牌合約已含 API）**：若爽爽 Shabu 既有簽訂之 inline 合約已解鎖 API 權限 → **費用為 0 元**。
  - **情境 2（向 inline 原廠加購 API 模組）**：依市場行情，API 介接月租費約 **NT$ 1,000 ~ 2,500 元 / 店 / 月**，6 個月全品牌約需 **NT$ 6,000 ~ 15,000 元**。
  - **情境 3（零成本替代方案，推薦）**：
    - 顧客在社群點擊連結進入 inline 訂位時，以網址帶參數（URL Deeplink）自動在備註帶入優惠碼，**這部分完全免費**。
    - 23:00 判斷空桌時，改以「外場店長打烊前於後台勾選確認」，或「串接 Eats365 現場桌況模組」，即可避開 inline API 高額加購費用（**費用為 0 元**）。

### 2. Google Maps 商家評論（官方審核與抓取限制）
- **功能需求**：每日 23:00 批次讀取全門市當日所有新增評論，即時偵測 1~2 星負評以啟動熔斷隔離。
- **實務現況**：
  - **不能使用 Google Places API**：雖然 Places API 每月有 200 美元抵扣額，但 Google 官方強制限制**每次最多僅回傳 5 則評論**，無法確保抓到「當日所有最新負評」，不符合風控要求。
  - **必須使用官方 Google Business Profile (GBP) API**：Google 官方提供商家管理自身評論，**調用規費為 0 元**。但申請必須通過 Google 官方的人工企業開發者白名單審核（審查需 2~4 週）。
- **費用評估與備援方案**：
  - **情境 1（官方 GBP API 審核通過，推薦）**：自行擁有分店商家管理權限並通過審核 → **費用為 0 元**。
  - **情境 2（審核未過，改採第三方商業評論抓取 API）**：若無法通過審核，轉由合法第三方商業爬蟲 API（如 SerpApi / DataForSEO）自動抓取各店最新評論，每月約 NT$ 300 ~ 500 元，6 個月備援費用約 **NT$ 1,800 ~ 3,000 元**。
